# Documentation content audit — 2026-08-01

The folder reorganisation (`308af3e`) fixed *where* the documentation lived. This audit is
about *what it says*, and whether that is still true.

**Method:** ground truth read from `manifests/assessments.psd1`, `manifests/collectors/`,
`src/assess/rules/` and the collector definitions, then compared against every claim in
`docs/`.

---

## 1. Ground truth, as of this audit

| Measure | Actual | Source |
|---|---|---|
| Assessments in the registry | **46** | `manifests/assessments.psd1` |
| Rule files | **44** | `src/assess/rules/*.yaml` |
| Rules total | **395** | `- id:` entries |

## 2. Findings

### F1 — CRITICAL: an assessment silently lost its WAF rules *(fixed in this pass)*

`Assess: Storage` declared `Rules = @('caf.storage', 'waf.storage')` and
`Frameworks = @('CAF: Security', 'WAF: Reliability')`. **`waf.storage.yaml` was deleted in the
AB#6746 restructure** and its five rules redistributed into the real pillar files. The glob
matched nothing, contributed zero rules, and raised no error — while the page and the registry
went on advertising WAF Reliability coverage.

Nothing was checking. This is the same class as every other defect this project has shipped:
absence that renders identically to presence.

**Fixed:** the dangling pattern removed and the `Frameworks` line corrected.
`Build-AssessmentCatalog.ps1 -Check` and `tests/DocsAssessmentCatalog.Tests.ps1` now fail on
any dangling glob, so it cannot recur.

### F2 — There was no list of what Scout assesses *(fixed in this pass)*

The owner's words: *"there is no list of all the CAF/WAF assessments this solution does."*
Correct. The two pages that came closest disagreed with the product **and with each other**:

| Page | Claimed | Actual |
|---|---|---|
| `docs/assessment/assessment.md` | 24 registry entries | 46 |
| `docs/design/assessment-registry.md` | 23 entries | 46 |
| `docs/assessment/assessment.md` | 139 rules | 395 |
| `docs/index.md` | 240 collectors | 242 |

**Fixed:** `docs/reference/assessment-catalogue.md` is now generated by
`scripts/Build-AssessmentCatalog.ps1`, grouped into CAF / WAF / service-category slices /
specialised, with rule files and automated-vs-manual counts per assessment. Test-guarded, so
it cannot drift. Stale counts above corrected.

### F3 — The most important number in the product was never published

**225 of 395 rules (57%) are `manual: true`** — they cannot be decided by any collected data.
No page said so. A reader reasonably assumed "395 rules" meant 395 automated checks.

This single figure reframes what Scout is: for several assessments it produces a *worklist*,
not a *grade*. The new catalogue publishes automated-vs-manual per assessment and carries a
callout explaining what a manual rule is. Some assessments are **entirely** manual —
`caf.billing` is 6 of 6, `waf.ai` is 33 of 34 — and a reader is now able to see that before
running one and being disappointed by the output.

### F4 — Collector coverage was documented; what each collector *collects* is not

`docs/reference/arm-modules.md` is generated, current at 242, and lists **Module → Resource
Type** per category. That answers "what is covered". It does **not** answer "what fields come
back", which is what someone reads before trusting a worksheet.

**Not fixed — recommended.** The collector definitions already declare their output shape, so
this is generatable from the same manifests rather than hand-written. Should extend
`Build-ArmModuleCatalog.ps1` rather than becoming a new hand-maintained page.

### F5 — Editorial that the restructure invalidated

`docs/assessment/assessment.md` and `docs/design/assessment-registry.md` both carry warning
callouts arguing that the registry count "is not N assessments" — that `LandingZone` is the
one real assessment and the rest are narrow views over it. **That was true when written and is
now questionable:** the AB#6746 restructure deliberately created per-pillar and
per-design-area assessments as distinct scored things.

**Counts corrected; the surrounding argument left standing and flagged here.** Rewriting it
needs a judgement about the current intent of the registry, and guessing at that is what
caused the reporting-epic mess. It needs the owner, or a deliberate decision recorded in
`docs/design/decisions/`.

### F6 — Readability: the site is fragmented

The owner's words: *"the site needs to be more readable, it is all broken up."* Structural
causes, beyond the folder layout already fixed:

- **No landing page per section.** `guide/`, `reference/`, `assessment/` have no index, so the
  sidebar is the only navigation and every page is an island. `frameworks/` has a README that
  works well as one — that pattern should be repeated.
- **`assessment.md` is 559 lines** covering architecture, permissions, the registry, the
  wizard and output formats. It should be split, now that there is a section to split it into.
- **Duplication across pages.** Permissions are described in `guide/permissions.md`,
  `assessment/assessment-permissions.md` and inside `assessment.md`. Three descriptions of one
  thing drift apart — and have.
- **Counts restated in prose across ~10 pages.** Every restatement is a future defect. The two
  generated catalogues are the fix; remaining prose counts should link to them rather than
  repeat them.

### F7 — CAF/WAF framework pages are enumerations, not coverage statements

`docs/frameworks/*` faithfully enumerate each published framework — and `FrameworkCurrency.Tests.ps1`
keeps them fresh, which is genuinely good. What no page states is **how much of each framework
Scout actually covers**. The audit found this once already (`pmo/audits/AB6447-caf-waf-coverage-audit.md`:
CAF ~10%, WAF ~15%) but those figures live only in a PMO audit, not in the documentation a user
reads.

**Recommended:** publish per-framework coverage — enumerated items vs items with a rule — from
the same generated pass. Coverage claims that are not generated will drift, exactly as the
collector catalogue did before AB#6741.
